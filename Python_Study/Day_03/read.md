## 1. 템플릿 메서드 패턴 (Template Method Pattern)
**템플릿 메서드 패턴**은 알고리즘의 **구조**를 부모 클래스에서 정의하고, 변화가 필요한 **세부 단계**만 자식 클래스에서 구현하도록 하는 디자인 패턴입니다.

### 핵심 설계 (The Skeleton)
부모 클래스인 `VendingMachine`의 `serve()` 메서드는 전체 운영 시나리오를 정의하는 템플릿 메서드 입니다. 어떤 자판기든 이 순서를 따라 작동합니다.

```python
# vender.py 중 템플릿 메서드 부분
def serve(self):
    amount = self.cost()             # 1단계: 금액 안내 및 입금
    if not self.cost_check(amount):  # 2단계: 금액 검증
        return
    self.prepare_product()           # 3단계: 제품 준비 (인터페이스만 구현)
    self.serve_product()             # 4단계: 제품 배출
    self.return_charge(amount)       # 5단계: 거스름돈 반환
```

## 2. 인터페이스의 활용
공통 로직(돈 계산, 배출 안내)은 부모에게 맡기고 다른 부분만 골라 구현함으로써 **코드 중복을 방지하고 가독성을 높였습니다.**
부모가 정해준 뼈대 안에서, 각 자판기는 오직 자신만의 `prepare_product` 로직에만 집중합니다.

부모 클래스에서 `prepare_product`를 **추상 메서드(Abstract Method)**로 선언함으로써, **인터페이스(Interface)** 역할을 하게 만들었습니다. 이는 자식 클래스들에게 "제품을 준비하는 로직"을 강제합니다.

* **커피 자판기**: 원두 추출 및 컵 세팅 로직으로 인터페이스 구현.
* **라면 자판기**: 컵면 배출 및 온수 주입 로직으로 인터페이스 구현.
* **콜라 자판기**: 재고 확인 및 캔 이동 로직으로 인터페이스 구현.

이를 통해 부모 클래스는 구체적인 방법(How)은 몰라도, 해당 동작이 존재함(What)을 확신하고 전체 흐름을 제어할 수 있습니다.

## 3. 구조의 진화

처음에는 학습용으로 한 파일에 모든 코드를 넣었지만, 실제 프로젝트 구조를 고민하며 다음과 같이 진화했습니다.

### 문제상황: 단순 파일 분리
모든 자판기 클래스를 개별 파일로 분리했더니, `main.py`가 직접 모든 자판기 객체를 import 해야하고, 새로운 자판기가 추가될 때마다 `main.py`를 수정해야 했습니다.

### Manager와 Centralized List 도입
이를 해결하기 위해 **관리자(`Manager`)**와 **창고(`vender_list`)** 개념을 도입하여 책임을 분리했습니다.

1. **`vender_list.py`**: 모든 자판기 객체를 리스트 하나에 모아 관리합니다.
2. **`Manager.py`**: 리스트를 받아 이름 기반의 "딕셔너리"로 변환하며, `main`의 요청에 따라 적절한 객체를 반환합니다.
3. **`main.py`**: 이제 `Manager` 객체 하나만 임포트하면 모든 자판기 기능을 제어할 수 있는 깔끔한 구조가 되었습니다.

## 4. 최종 아키텍처의 장점
* **확장성(Scalability)**: 새로운 자판기 추가 시 `main` 코드를 수정할 필요가 없습니다. (OCP 준수)
* **캡슐화(Encapsulation)**: 입금 처리나 예외 처리 등 복잡한 로직은 `serve` 메서드 내부에 숨겨져 보호받습니다.
* **유지보수성(Maintainability)**: 설계(Base), 구현(List), 관리(Manager), 실행(Main)의 역할이 명확히 분리되었습니다.
